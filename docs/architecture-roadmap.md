# 整体迁移路线 v2 与不可变边界

本路线以当前仓库的真实边界为起点：S0 数据契约、S1 识图宿主、S2 地图识别和 S3 上游原生战役流程已经完成验收；C# 目前承担数据消费、设备抽象、页面导航、批量编排和结果报告，尚不是独立的 C# 关卡引擎。后续目标是逐步扩大 C# 的通用产品能力，同时保持上游规则和识图语义只有一个真值来源。

## 当前基线

以下能力在路线 v2 中视为冻结基线，后续阶段只能在其上增加能力：

- 数据链已经覆盖素材、地图 IR、章节 `Config`、继承、来源和漂移校验；JSON 是离线契约，不是运行时战斗配置。
- 识图、页面规则、地图检测和 OCR 通过 `IVisionEngine` 进入上游宿主；C# 的 `Imaging` 目录只作对拍证据。
- S3 生产路径使用上游 `CampaignRun.load_campaign()`、章节 `Config` 合并、`MAP`、入口准备和原生 `Campaign.run()`；不完整 IR 不能被当成可重放计划。
- 真跑结果已经区分成功、撤退、错误和未知退出；`CampaignEnd` 本身只表示流程结束，不能单独证明清图。
- 结果口径已经冻结为 `sortie-result/1` 合同（两侧实现 + 逐例对拍 + 静态守卫）；后续任何结果判定都必须过合同，不得在调用点自己拼 `cleared`。

### R3：原生钩子与高频能力迁移

目标是按导出器的 `native_overrides`、调用词表和依赖闭包迁移通用 C# 能力。先做高频、低耦合、可对拍的操作，再做依赖地图状态和复杂继承的钩子；上游原生实现始终保留为基准和回退路径。

迁移顺序由覆盖率、依赖数量和可验证性决定，不由某个地图是否失败决定。每个迁移项需要上游调用轨迹、C# 结果轨迹和失败语义对拍；对拍不完整就继续走上游宿主。

阶段门槛：迁移项在跨域样本上通过行为对拍，包含正常、失败、撤退和重试路径；不存在只对单张地图有效的阈值、坐标或路线。

**状态：候选已量化，结论是"原生钩子不是 R3 的合适起点"**（证据见下）。

| 依据 | 数据 | 出处 |

识图不在 C# 重写（铁律 2），地图/导航状态属于上游对象图。
把钩子搬进 C#，要么重写识图（已被逐项实测证伪），要么把上游地图引擎一起搬（等于 R5 的宿主替换，
需要逐项对拍 + 性能基准 + 可回退开关，现在没有这些证据）。
所以"高频、低耦合、可对拍"这三个条件，原生钩子一个都不满足。

**R3 的可行方向**（待下一轮按此推进）：

1. ~~**模板/数据集驱动的通用算子**：从导出器词表（`docs/s3-plan-vocabulary.md`）里挑**纯函数**算子~~
   —— **这条已被词表数据否掉**（2026-09-23 核对）：词表 57 个调用里**高频项全是引擎动作**，
   tier A（1000 章）只用到 9 个调用，其中前 5 个就占了绝大部分次数：

2. **设备在线后仍须逐项行为对拍**：当前模拟器可用于真机样本，但还没有具备相同输入、输出与失败语义的 C# 迁移候选；

**因此当前 R3 仍未达到迁移门槛**：钩子与视觉/地图状态耦合（见上表），

### R5：宿主替换评估

只有在 R0-R4 稳定后，才评估把某些识图或设备能力替换成 C#。替换必须以逐项对拍、性能基准、真实产品路径和可回退开关为前提；未达到全部证据时继续使用上游宿主，不为了“纯 C#”提前重写。

## 长期不能变动的规则

- 生产战役必须经过上游 `CampaignRun.load_campaign()`、章节 `Config` 合并和原生 `Campaign.run()`；不得把静态 JSON 计划当成运行时真值。
- 视觉、页面、OCR 和地图检测必须从上游模块对象解析；不得从 `assets.json` 重建运行时规则，不得维护第二份素材或地图特例表。
- 不得在 C# 适配层按地图名称、编号、尺寸、服务器或少数案例增加坐标、阈值、机位、路线、寻敌或战斗分支。失败先查通用调用链、状态清理和客户端兼容层。
- C# 图像实现只能作为参考实现和对拍基准；没有逐项证据，不得替换上游宿主。
- `CampaignEnd`、威胁百分比、单张截图、撤退、超时和未知退出都不能单独作为通关证明；通关必须有成功结算并返回章节页的证据。
- 新业务域必须先进入 `Alas.Core` 的通用任务/状态模型，再接入 CLI 或前端；不得在命令分支里复制业务状态机。
- 修改上述边界时，提交必须说明通用根因、保持的上游语义、影响范围、阶段门槛和新增回归证据；没有这些证据不得改变冻结基线。

架构守卫 `tools/diagnostics/verify_architecture.py` 检查生产入口、集中路径、素材模型、迁移路线和地图特例；它已接入 `verify_all.py` 与 `sync_all.py --update --verify`。

## 附二：R4 框架选型**决定**（第 169 轮，自主决定）

**决定：暂不引入前端框架。** 继续用"生成期把结构排好"的单文件静态视图
（`tools/report_html.py` + 17 项断言），直到出现下面列出的触发条件之一。

### 理由（按重要性排序）

1. **目前所有需求都能被静态视图满足**：看结论、看失败、看任务/关卡明细、看证据原文、跳转 ——

2. **框架带来的收益要"多人长期使用"才出现**，而现在的使用者是一个人 + 一个 Agent；
   它要付的代价却是立刻的：构建链、依赖、以及与"单文件可拷走/可直接发出去"的特性冲突；
3. **与本项目的铁律同向**：不引入会形成"第二份真相"的东西。前端框架会自然诱导出

4. **数据面仍在演进**：九个域、报告字段、停止语义最近几轮还在改。**先把数据面稳定下来**，
   再谈用框架消费它，比反过来便宜得多。

### 重评触发条件（写清，避免以后凭感觉重开）

出现任一条就该重评，而不是"想加就加"：

* **实时性**：需要在运行过程中持续刷新（现在是一次性生成、刷新页面即可）；
* **规模**：运行次数/条目数大到静态页难以浏览（如单页上千行、需要分页或搜索）；

* **交互**：出现必须由前端状态驱动的操作（如"在这里点按钮改队列并立即看到结果"）。

## 附三：R5 性能基准 #1 —— 跨语言调用开销与宿主冷启动（2026-09-23 实测）

R5 的门槛之一是"**性能基准**（替换后不慢于宿主路径，含冷启动、内存、跨语言开销）"。
这是它的第一组数（同机实测，`ping` 这种无副作用的 op，N=300）：

| 量 | 实测 | 说明 |
| --- | --- | --- |
| 单次 op 往返（稳态） | **≈ 0.01 ms / 次**（300 次共 3.9 ms，10 µs 量级） | 走 `handle_line` 的 JSON 往返：C# → 宿主 → C# |
| 宿主模块冷导入（`import alas_vision`） | **≈ 270–293 ms** | 进程内一次性成本（首次导入该模块，含其依赖） |
| `ping` 首调 | 0.0 ms | 该 op 无初始化；有状态的 op（如设备/OCR）另计 |

**复现**：`python` 起一个脚本（`tools` 入 path + `chdir` 到 `.runtime/engine`），
`import alas_vision` 计时；再 `json.loads(av.handle_line(json.dumps({'id':1,'op':'ping','args':{}})))`
循环 300 次计时。脚本属一次性测量，未入库（要长期跟踪应做成 `verify_*` 步骤）。

**这组数对 R5 的直接含义（重要）**：

1. **跨语言边界不是瓶颈**（10 µs 量级）。所以"为了更快而把胶水层搬到 C#"这类候选，
   收益上限就是这个量级 —— **不值得**；
2. 真正的成本在**边界两侧的工作量**：设备 I/O（截图 ~0.3 s/帧、控制点击）、
   以及宿主内的识图/OCR（单次 OCR 约 10 ms 量级）。R5 的候选应当选
   "**两侧工作量差得远**"的能力，而不是"边界本身"；
3. 冷启动 ≈ 0.3 s 是**一次性**的，与"每次运行"的成本相比可忽略 ——
   所以"减少进程间往返"也不能成为 R5 的理由（本来就没有进程间往返：宿主是同进程的）。

**尚未测（如实标注）**：内存占用、真实截图/OCR 端到端吞吐、
以及"若把某能力搬到 C# 后"的对照数（那要先有候选实现）。

## 附四：R5 性能基准 #2 —— 冷启动到首帧、稳态抓帧（2026-09-23 实测，设备在线）

延续附三（跨语言往返 10 µs）。这一组量的是**一次运行真正要付的成本**：

| 量 | 实测 | 含义 |
| --- | --- | --- |
| `import alas_vision` | **267 ms** | 宿主模块冷导入（与附三的 270–293 ms 一致） |
| **冷启动到首帧**（含设备/引擎初始化 + 第一帧） | **2258 ms** | 一次运行的**一次性**成本，约 2.3 秒 |
| **稳态抓帧** | **340 / 354 / 352 / 348 / 338 ms → 均值 346 ms** | **每次抓帧约 0.35 秒**，这是整次运行的**最大单项成本** |

对照上一轮真机跑的真实日志：一场战斗约 20 秒、一次科研/宿舍任务 13–15 秒；
按 0.35 s/帧估算，**运行时间里相当大一块就是"等截图"**。
（宿主内 OCR 约 10 ms/次 —— 见宿舍任务日志 `[OCR_DORM_FURNITURE_COIN 0.011s]`，比抓帧小两个数量级。）

**对 R5 的直接含义**：

1. **任何想"更快"的替换，都必须先跨过 0.35 s/帧这道坎** —— 而抓帧的耗时在**后端**（本机 ADB 通道），
   不在语言边界、也不在 C# 与宿主的接口上；
2. 所以 R5 的正确问题不是"把接口搬到 C#"，而是"**这个后端还能不能更快**" ——
   而这件事**本来就有配置旋钮**（`device_configure` 可换 `Emulator_ScreenshotMethod`），
   属于"换配置"而不是"换实现"：**R5 在这里没有立足点**（不该为了它重写宿主）；
3. 反过来，**如果**哪天真要把某能力搬到 C#，判据应当类似：先把"这块到底花多少时间"量出来
   （本例：抓帧 0.35 s vs OCR 0.01 s vs 边界 0.00001 s），再决定值不值得动。

**未测（如实标注）**：内存占用 · 各截图后端的对照（`adb` / `nemu` / `droidcast` …，属"换配置"实验，
可作为 R4/R5 之外的独立优化项）· 真实战斗的端到端耗时分解（需要一次带计时的真机跑）。

## 附五：抓帧后端对照实验（**待做**，设计已定；不属于 R5，但可能是最大的一笔优化）

附四量到：本机抓帧 **~0.35 s/帧**（`adb` 后端，两次独立测量 346 / 306.8 ms），
而它是整次运行的最大单项成本（一场战斗 ~20 s ≈ 数十帧）。宿主内 OCR 只有 ~10 ms/次。

**它为什么不属于 R5**：耗时在**后端**，不在语言边界、也不在 C#/宿主接口；而上游本来就有
`Emulator_ScreenshotMethod` 这个旋钮 —— **这是"换配置"，不是"换实现"**。
但它可能是**收益最大**的一笔：若某个后端能到 ~0.05 s/帧，整次运行的墙钟时间会明显下降。

### 实验设计（照着做，不要重新想）

| 步 | 做什么 | 命令 / 判据 |
| --- | --- | --- |
| 1 | 列出本机可用的截图后端 | `module/device/method/` 下的实现；上游 `Emulator_ScreenshotMethod` 的候选值 |
| 2 | 逐个配置并测抓帧 | 每个后端：`device_configure(serial, screenshot=<method>)` → 连续 10 次 `device_capture_set(raw=True)`，记均值与波动 |
| 3 | 同时验**控制**通道 | 抓帧快但点击慢没有意义：同一次配置里量点击（`device_click` 的 ms）与一次真实点按的端到端 |
| 4 | 只看**合法组合** | 上游对"截图 × 控制"有搭配要求（如 scrcpy 配 minitouch/MaaTouch）；不合法组合的报错也要如实记 |
| 5 | 落到一处 | 结果写进本节表格（后端 / 抓帧均值 / 点击均值 / 备注），并给结论：**默认该用哪个** |

### 预期与判据

* **有收益**：某后端抓帧均值 ≤ 0.15 s 且控制通道正常 → 建议改默认配置，并跑一次真机战斗
  对照墙钟时间（当前一场战斗约 20 s）；
* **无收益**：全部后端都在 0.3 s 量级 → 说明这台模拟器的通道本身如此，**从此不要再为"抓帧慢"找 R5 的理由**。

**这一步的价值不只是省时间**：它把"运行到底慢在哪"钉成一个可复现的数字，
之后任何"要不要为性能改点什么"的讨论都从这张表出发。

### 附五实测（2026-09-23，第一次：三个后端）

| 后端 | 单次耗时（连续 5 次，单位 ms） | 均值 | 备注 |
| --- | --- | --- | --- |
| `adb`（当前配置） | 340 / 354 / 352 / 348 / 338 | **346** | 另一次独立测量 306.8 ms；本次序列里也复现了 ~306–346 区间 |
| `droidcast` | 393 / 296 / 302 / 299 / 306 | **319** | 与 adb 无实质差别 |
| **`nemu_ipc`** | **2455 / 8 / 7 / 7 / 7** | 497（被首帧拉高） | **稳态 7–8 ms/帧，比 adb 快约 45 倍**；但**未验证新鲜度**，见下 |

配置切换与还原都验过：`device_configure(screenshot=…)` 会写 `alas.json`，
测完已从备份还原，**哈希一致**（`Alas.Emulator.ScreenshotMethod` 仍是 `adb`）。

### ⚠️ `nemu_ipc` 的 7 ms **还不能当成结论**（待验证，别急着改默认）

这正是"数好得可疑，先怀疑测量"的情形。三个必须补的验证：

1. **帧是否新鲜**：连续抓帧存成数组做逐像素比较 —— 主界面有 Live2D 动画，真帧应有差异；
   若连抓三帧**逐字节相同**，那就是缓存图，7 ms 毫无意义。
   （本次尝试在取帧处踩了自己的坑：`av._state["image"]` 在该路径下是 `None`，
   需先查清 `device_capture_set` 把图存在哪个字段。）
2. **画面确实跟着变**：抓帧 → 做一次可预期的画面变化（如切页）→ 再抓帧，两帧必须不同；
3. **上游为什么警告**：日志里有 `nemu_ipc is not available on …` —— 要查清那条警告的含义
   （是"该模拟器版本不支持"，还是"仅在特定条件下可用"）。**上游自己的怀疑优先于我的乐观。**

**在 1-3 完成之前**：不改默认配置、不据此下任何性能结论。
判据仍按本节开头那条：只有"抓帧均值 ≤0.15 s **且**控制通道正常 **且** 帧验证为真"才建议切换。

### ⚠️ 附五更正（2026-09-23，同日验证）：`nemu_ipc` 的 7 ms **是失败路径**，不能改默认

对上一小节的"待验证"做了验证，结论是**否掉那个数**：

```
=== nemu_ipc ===  配置 ok=True（device_configure 不报错）
NemuIpcError: Connection failed, please … / Emulator info incorrect
  第1次 4506.2 ms   返回键=[]   error=RequestHumanTakeover: …
  第2次    7.6 ms   返回键=[]   error=RequestHumanTakeover: …
  第3次    6.9 ms   返回键=[]   error=RequestHumanTakeover: …
  _state['image'] is None ?  True          ← **一帧都没有**

=== adb ===（对照）
  第1次 437.1 ms   返回键=['capture_ms','method','raw','shape']  error=None
  _state['image'] is None ?  False         ← 帧有效
```

**所以那"稳态 7 ms"是抓帧失败的耗时**（`RequestHumanTakeover`，帧为空），
**不是 45 倍加速**。`device_configure` 会照单接受这个后端（`ok=True`），错误要到真抓帧才暴露 ——
如果按那个数去改默认，结果是**每一帧都拿不到**（所有依赖画面的判断全线失效），比"慢"糟糕得多。

**由此得到一条要写进纪律的判据**：

> **耗时要与"成功判据"一起看。** 只测时间的基准会把"快速失败"记成"性能优异"。
> 本次的验证手段很便宜：看 op 返回里有没有 `error`、返回键是否含 `capture_ms/shape`、
> 以及 `_state['image']` 是否真的被写入。

**修正后的默认建议**：仍是 `adb`（唯一验证过"抓帧成功 + 帧有效"的后端）。
`droidcast` 的 319 ms **尚未验证帧有效性**（同一批测量里只看了耗时）—— 要它进候选，
先按上面三条验一遍。`nemu_ipc` 在本机**不可用**（连接失败），除非修好连接否则不必再测。

### 附五最终表（2026-09-23，**每个后端都过了"成功判据"这一关**）

验证协议（便宜且够用）：配置后连抓 3 帧，看 **① op 返回有没有 `error`、② 返回键是否含 `capture_ms`/`shape`、③ `_state['image']` 是否真被写入**。

| 后端 | 配置接受 | **帧有效** | 抓帧耗时（外层 / op 自报 `capture_ms`） | 结论 |
| --- | --- | --- | --- | --- |
| `adb`（当前默认） | ✅ | ✅ | 437/361/367 ms（312/314/326） | **保持默认**：唯一从头用到尾、且反复验证过的后端 |
| `droidcast` | ✅ | ✅（本轮验证） | 2300/307/290 ms（280/257/243） | **可用且略快约 15%**；作为已验证备选记录在案 |
| `nemu_ipc` | ✅（照单接受） | ❌ **无帧** | 4506/7.6/6.9 ms（无 `capture_ms`，error=`RequestHumanTakeover`） | **不可用**（`NemuIpcError: Connection failed`）；除非修好连接，不必再测 |

**对"要不要改默认"的结论**：**不改**。droidcast 快 ~15%，不足以抵消"换掉一条用了整夜、且所有真机结论都建立在它之上"的风险；
真要提速，应当先在**同一次真机战斗**里对照两者的墙钟时间（而不是只看抓帧单点），
并确认 droidcast 在长时间运行下不退化 —— **这两条都还没做**。

**下一步（建议做成常驻工具）**：把上面那个"验证协议"做成 `tools/diagnostics/verify_device_backends.py`：
配置每个后端 → 抓 3 帧 → 断言三条成功判据 → 输出这张表（耗时**只在帧有效时**才计入）。
本次是手工做的；**做成脚本后，以后任何"换个后端试试"的念头都会被同一套判据约束**，
不会再出现"把快速失败记成性能优异"这种事。

## 附六：R5 性能基准 #3 —— 内存（2026-09-23 实测，补齐门槛的三条轴）

| 阶段 | RSS | 增量 |
| --- | --- | --- |
| 裸解释器 | **15.3 MB** | — |
| + `import alas_vision`（宿主模块） | **28.3 MB** | +13.0 MB |
| + **引擎/设备层 + 首帧** | **136.8 MB** | **+108.5 MB** |

**方法**：同一进程内用 `K32GetProcessMemoryInfo` 读 `WorkingSetSize`（ctypes；第一版用了
`psapi.GetProcessMemoryInfo` 静默返回 0，换成 `kernel32.K32GetProcessMemoryInfo` 并检查返回值才对）。
触发引擎加载的方式是跑一次真抓帧（`device_capture_set`，ok=True）。

**口径说明**：测的是**同一套引擎在进程里加载**的成本。产品里宿主与 C# **同进程**
（R1 的设计），所以这份内存也计在 `alashub` 进程头上（C# 侧自身占用未单独测）。

### 门槛"性能基准"到此三条轴齐了，而且**三条指向同一个结论**

| 轴 | 实测 | 对 R5 的含义 |
| --- | --- | --- |
| 跨语言开销 | **10 µs/次**（附三） | 边界不是瓶颈 → "搬接口到 C#" 不值得 |
| 冷启动 | **~2.3 s**（附四；含 import 270 ms + 设备初始化 + 首帧） | 一次性，且宿主同进程 → "减少往返"不是理由 |
| **内存** | **~137 MB**（本附；其中引擎/设备层 ~108 MB） | **引擎是全局依赖**：只把某一项能力搬到 C#，这份内存**一分都省不掉** → "省内存"也不是 R5 的理由 |

**所以 R5 的正确形态被这三组数夹出来了**：能被考虑的对象只能是
"**其唯一真相本来就在 C# 侧**"的能力（见附一的一句话判断法）；
任何"部分替换宿主能力以换取更快/更省内存"的想法，都被这三组数否定 ——
**因为瓶颈（设备 I/O 0.35 s/帧、引擎内存 108 MB）不在被替换的那一层。**

## 附七：R5 阶段性结论 —— **没有候选能过门槛；R5 的意图其实已经实现**

写这一节是因为：三组性能基准（附三/四/六）加上铁律，已经把候选空间夹到很小；
再往下推之前，应该先把"**为什么不推**"用证据说清，免得下一轮从头再想一遍。

### 逐个候选过一遍（判据=附一那句话：唯一真相本来就在 C# 侧吗？）

| 候选 | 唯一真相在 C# 侧？ | 性能上能赢？ | 结论 |
| --- | --- | --- | --- |
| 页面 / 素材 / 地图识别规则 | ❌ 在上游（`module.*.assets`、`page.py`、`MAP`） | — | **非候选**（铁律：不得从 `assets.json` 重建、不得复制规则表） |
| 章节 `Config` / `MAP` / 原生 `Campaign.run()` | ❌ 在上游 | — | **非候选**（生产战役必须继续走上游） |
| 识图 / OCR | ❌ 上游语义 | 抓帧 0.35 s/帧、OCR ~10 ms/次；瓶颈在后端与设备，不在这一层 | 无可赢之处 |
| 设备 I/O | ❌ 上游后端抽象 | 已量：换成 droidcast 只快 ~15%，nemu_ipc 直接不可用（附五） | **换配置的事，不是替换实现** |
| 导航 | ❌ 页面图与流程均来自上游 | `NavigateTask` 调用上游 `UI.ui_ensure()` | 保持上游语义，不迁移逐页面流程 |
| 内存"省一点" | — | 引擎/设备层占 108 MB 且是**全局依赖**，只搬一项一分不省（附六） | 不成立 |
| 跨语言开销"省一点" | — | 10 µs/次（附三） | 不成立 |

### 而且：R5 的**意图**已经有两处实例

R5 想验证的是"C# 能不能拥有本来就属于它的那部分"。已经拥有的两处，**而且都有逐项对拍**：

1. **结果判定**：`sortie-result/1` 合同两侧各实现一份，`verify_result_contract.py` **35 例逐例对拍**（R0 的核心交付）；
2. **地图模型解析**：`verify_map_ir.py` 把 C# 解析结果与**上游活对象**对照，**11/11 匹配 + 网格指纹 11/11**（该脚本曾烂在套件之外，第 149 轮修好并纳入）。

这两处正好是"唯一真相在 C# 侧（或 C# 作为消费方）+ 有逐项对拍"的形态 ——
**R5 该做的事，在这两个地方已经做过了。**

### 结论与重评触发条件

**结论**：以现有证据，**R5 没有可推进的候选** —— 不是"没时间做"，而是
"**每个方向都被实测数或铁律挡住**"。`CampaignEnd`/合同/上游语义那条线继续由上游持有。

**出现以下任一条就重评**（写清，避免凭感觉重开）：

1. 出现某能力，其**唯一真相本来就在 C# 侧**，且上游那份实现成为瓶颈或阻碍 C# 侧功能；
2. 上游移除/改写某能力，导致继续使用它的成本高于自持（那时是"被动迁移"，不是"主动替换"）；
3. 性能画像发生变化：例如换了后端后设备 I/O 不再是瓶颈（附五的表要重测），
   而某个**非规则类**能力成为新的最大项。

**在这一节被推翻之前**：R5 的工作量应当为零 —— 力气投到 R4 的界面与 R2 的动作域上。
